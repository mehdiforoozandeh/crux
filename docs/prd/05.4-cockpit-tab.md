# PRD: 05.4 — the cockpit tab

- **Kind:** feature
- **Spec:** [.spec/05-autopilot.md](../../.spec/05-autopilot.md) §15 — 05.x series, after [05.3](05.3-agents.md)
- **Signed off 2026-09-18** by the PI, as written — every design decision below is settled.
- **Engine version:** `3.3`, **unchanged**. Nothing here changes the vault format, the verdict,
  the roll-up, or `engine.snapshot`'s output. No migration.

## Problem / motivation

An autopilot run is currently invisible. `crux auto status` prints four numbers at a terminal;
everything else a PI would want mid-flight — is the score moving, which island is working, how
much budget is left, why it stopped — is in two files nobody reads by hand: `auto/<qid>/state.json`
(26 keys, rewritten whole after every event) and `auto/<qid>/ledger.jsonl` (21 event names,
append-only). 05.3's own docstring says who they were frozen for: *"a reader (the cockpit, 05.4)
must never meet a shape that depends on how far the run got"* ([engine.py:6696](../../skills/crux/scaffold/engine.py)).

Worse, a run today makes the cockpit **slower**, not just uninformative. The snapshot cache is
keyed on `vault_stat_key`, one `os.walk` of the whole vault
([serve.py:69](../../skills/crux/scaffold/serve.py)). `auto/` is a plain, non-hidden directory
inside the vault, and the driver rewrites `state.json` and appends to `ledger.jsonl` inside one
lock hold after **every** event. So during a run the key moves constantly, the cache misses on
every 1 Hz poll, and `engine.snapshot()` rebuilds the entire tree each time — the 29 ms / 181
file-reads per second that spec 12's measurement existed to kill. **That defect is live on `main`
today**, with no cockpit tab involved at all. This slice fixes it, because it is the exact failure
spec §15 forbids and the tab would otherwise be blamed for it.

Three things this slice delivers, in the spec's words: the endpoint, the two views, the live mark
on the tree.

## Design decision

### A · `/auto.json` — one small endpoint that never touches the tree

A fourth route beside `/snapshot.json`, `/wiki/<slug>.json`, `/rd/<slug>.json` and `/file/`, added
to the same `do_GET` if-chain ([serve.py:167](../../skills/crux/scaffold/serve.py)) and served
through the same `_send_json`, with its own cache triple on the server object
(`auto_key` / `auto_data` / `auto_etag`) under its own lock, mirroring `_snapshot` exactly. Same
ETag contract: a content sha, a 304 on `If-None-Match`, `Cache-Control: no-store`.

Its payload is built by **one new pure engine function, `auto_cockpit(root)`**, which reads
`auto/<qid>/state.json`, `auto/<qid>/ledger.jsonl` and `auto/<qid>/plan.md` **and nothing else**.
The third file is read for one reason only: the objective's `direction` is in neither of the other
two (`island-best`'s `from`/`to` are git ref SHAs, not scores — see the table below), and
`auto_portfolio` cannot rank without it. The read is `parse_flight_plan(read(...))` — total, pure,
text→dict. It does not construct a `Vault`. It does not parse a node. It does not call
`resolve_address`. It does not call `auto_island_attempts`, which builds a whole `Vault(root)` and
is therefore exactly the thing this endpoint exists to avoid.

**That is provable, not a promise.** The acceptance criteria include a check that monkeypatches
`engine.Vault` to raise and asserts `auto_cockpit` still returns a full payload. A later change
that reaches for the tree fails that check by construction.

**Everything the two views need is already in the ledger**, which is why this is possible at all —
05.3 froze the fields:

| what the view needs | where it comes from |
|---|---|
| score against attempt number | `scored` → `{attempt, seed, value}` |
| lineage (`builds_on`), island, title | `node-filed` → `{attempt, island, parent, builds_on, title}` |
| verdict and closing value | `closed` → `{attempt, verdict, value, island, task}` |
| the island's best and when it moved | `island-best` → `{attempt, island, branch, from, to, score}`; `from`/`to` are git ref SHAs, not scores — the score is `score` alone, and this is also why the objective's `direction` cannot be recovered from the ledger at all |
| what is in flight, per island | `state["in_flight"]` → `{island, parent, from, phase, worker_tries, scorer_tries, pid, failure, started}` |
| the budget axes | `state["budget"]` → three axes, each `{used, total}` |
| why it stopped | `state["stop"]` → `{reason, axis, attempt, detail, at}` |
| agent cooldowns, steward guidance | `state["agents"]`, `state["steward"]` |

**Rejected: an `auto` key on the tree snapshot.** It is what spec §15 forbids in one sentence, the
snapshot's top-level key set is pinned to eleven names by
[selftest.py:543](../../skills/crux/scaffold/selftest.py), and a growing payload behind a cache the
run itself invalidates is the melt this slice is fixing. That pin stays at eleven and the
criteria assert it.

**Rejected: a websocket or server-sent events.** The cockpit is a 1 Hz ETag poll everywhere else;
a second transport is a second failure mode for no gain at this size.

### B · `vault_stat_key` stops walking `auto/`

`engine.snapshot` reads nothing under `auto/` — verified by grep, and asserted by a new check. So
a write under `auto/` **cannot** change the snapshot's content, and invalidating its cache on one
is pure waste. The fix is to skip `auto` in the walk beside the hidden directories already
skipped, with the reason written in the docstring.

This is a behaviour change to a cached read, so it gets its own assertions both ways: appending a
byte to `auto/<qid>/ledger.jsonl` must **not** move the key; touching a node file must. The
existing blind spot the docstring already documents (a same-size, same-tick edit) is unchanged.

**Verified, not assumed** (run on `main` at `d25e3ec`, 2026-09-18): on a fresh vault,
`engine.snapshot(root)` is **byte-identical** after writing `state.json`, `ledger.jsonl` and
`plan.md` under `auto/q1/`; and `serve.vault_stat_key` **moves** on a single further ledger append.
That is the defect in two lines — the cache misses on a write that cannot change the content.

**Rejected: leaving it and living with the rebuild.** A 200-attempt run would spend a core-second
per second rebuilding a tree whose content did not change. The tab is the reason we noticed; the
defect is not the tab's.

### C · The tab appears only when the vault has a run

`updateTabs` already hides the Wiki and Taskhub tabs on a vault whose data is inactive
([app.js:2017](../../skills/crux/scaffold/webui/app.js)), and drops back to Tree if the active tab
goes inactive. The Autopilot tab follows that convention exactly: `auto.json` carries
`active: false` on a vault with no `auto/` directory, and the tab is hidden. **A vault that never
met autopilot reads exactly as it does today** — `auto_cockpit` creates nothing, not even `auto/`,
the same rule `auto_status` already keeps.

Tab label **Autopilot**, `data-tab="auto"`, fourth in the nav after Taskhub. The last-tab memory
(`localStorage["crux-tab"]`) gains `"auto"`.

### D · Two views on a rail, the Taskhub's own pattern

The spec says *two views on a rail as the Taskhub already has*. The Taskhub's rail in fact carries
**four** (`TASK_VIEWS` — Frontier, All, By category, Experiment timeline,
[app.js:2623](../../skills/crux/scaffold/webui/app.js)); what the spec is pointing at is the rail
**pattern**, not the count. Autopilot gets two, as §15 names them.

`AUTO_VIEWS = [["live", "Live"], ["results", "Results"]]` — the literal shape of `TASK_VIEWS` —
rendered into an `#auto-rail-body`
inside an `#auto-pane` that copies `#tasks-pane`'s markup. Selection is client-side state
persisted as `localStorage["crux-auto-view"]`, exactly as the Taskhub persists `crux-tasks-view`.
Clicks are handled by a listener on `#auto-pane`, not on `#tabs` — the Taskhub carries a comment
recording that the other choice left its rail dead.

**Several runs in one vault** (the spec's third open question, unresolved) needs no answer here:
`auto.json` carries a `runs` list keyed by anchor, and a **Run** group appears in the rail only
when there is more than one. With one run — every case today — the rail is exactly two buttons.
`auto_status`'s CLI behaviour, which refuses to guess between several runs, is untouched.

### E · Live — the four panels §15 names

1. **Score against attempt number.** The spec calls this the fastest read on whether this is
   working. A hand-drawn SVG line-and-dot plot: one series per island, x = the attempt's ordinal
   in `closed` order, y = its `scored` value, the bar drawn as a rule, the running best as a step.
   **No chart library** — the only vendored file is `motion.js` and the standard-library-only rule
   binds the frontend too. An invalid run has no score and is drawn as a hollow mark on the axis,
   never as a zero: an invalid run measured nothing.
2. **In flight, per island.** One row per entry in `state["in_flight"]`, showing its phase
   (`reserved` · `drafted` · `committed` · `scored` · `closed`), its parent, its try counts and how
   long it has been going.
3. **The budget axes.** Three meters — attempts, hours, model calls — each `used of total`, using
   the same words `auto_stop`'s detail already uses, so the tab and the stop reason can never
   disagree.
4. **The ledger.** Newest-first, one row per event, with its `at`, its name and its fields.

### F · The ledger is tailed, not paged

A 200-attempt run's ledger is roughly 2,000 lines. `auto.json` carries the **last 200 events plus
the total count**, newest-first; the Live view's ledger panel has a *Show more* control that
re-requests with `?events=<n>`, capped at 2,000. No cursor, no page tokens, no second endpoint.
The tail is what a person reads mid-flight; the whole file is on disk for anyone who wants it.

**Rejected: shipping every event.** At ~180 bytes a line, a long run's ledger is ~400 kB re-sent
through the poll each time it changes, which is worse than the snapshot we just stopped rebuilding.

### G · Results — lineage and a diverse portfolio

- **Lineage from `builds_on`.** Each closed attempt's chain is read from the `node-filed` events,
  so the view draws the same forest the bandit selected over, per island, with the baseline at the
  root.
- **A diverse portfolio, not a winner.** ERA returns top-k diverse deliberately: one score is one
  evaluation. No portfolio rule exists in the engine yet, so this slice defines one pure function,
  `auto_portfolio(rows, direction, k=5)`: rank by score in the objective's direction, then take
  greedily, **skipping any candidate that is an ancestor or a descendant of one already taken**.
  Lineage is the diversity axis because it is the only one crux has for free — MAP-Elites'
  behaviour descriptors are rejected in spec §3 for exactly the reason that nobody writes them.
  The panel says in one line what the rule was, and marks the single best separately, so the
  portfolio is never mistaken for a ranking.
- Every row shows its verdict, and an `invalid-run` row is excluded from the portfolio — it
  measured nothing.

### H · Clicking an attempt opens the existing detail reader

An attempt is a node id, and the detail reader already opens a node by id from the snapshot. A row
whose node is in the snapshot is a button that selects it; a row that is only *reserved* — the id
exists but no node has been filed — is rendered plainly and is not clickable, with its phase as
the explanation. No second reader is built.

### I-0 · Liveness has no heartbeat, so the tab must not claim one

There is **no heartbeat field**. `state["driver"] = {pid, host}` is written at run open and reset
on every resume, and never again while the loop runs; `auto/.lock` is held only momentarily inside
each event, so a reader between events almost always finds it absent. `auto_run`'s own
same-host `_pid_alive` guard is the only liveness check in the codebase, and a cockpit reading a
vault over a network mount cannot use it.

So the tab reports **three** states, not two, and never asserts more than it knows:

| state | condition | how it reads |
|---|---|---|
| **running** | `stop` is null **and** `updated` is within 120 s | the live mark, the in-flight rows |
| **stale** | `stop` is null **and** `updated` is older than 120 s | *no driver write since <t>* — the mark is withdrawn |
| **stopped** | `stop` is set | the stop's reason and detail, verbatim |

The 120 s threshold is generous on purpose: a worker try can take minutes, but `_record` writes
`state.json` on **every** event inside the same lock hold, so a healthy driver in a normal attempt
writes several times a minute. The threshold is a named constant so it is one edit, not a magic
number, and the payload carries `updated` and the computed `liveness` so the frontend does no
clock arithmetic of its own.

**Rejected: adding a heartbeat write to the driver.** It would mean `autopilot.py` writing
`state.json` on a timer for the benefit of a viewer — a write the run does not need, on a file the
run's correctness depends on. The staleness read costs nothing and is honest about what it knows.

### I · The live mark: the missing half is the explanation, not the pulse

**The per-node mark already exists, and this slice must not add a second one.** The driver flips
an attempt's node to `running` the moment it starts testing
([autopilot.py:1621](../../skills/crux/scaffold/autopilot.py)), and `nodeSVG` already emits
`class="node running"` for exactly that ([app.js:483](../../skills/crux/scaffold/webui/app.js)),
which `style.css` animates as a pulse. `n.status` is already inside `treeSignatures`' **cosmetic**
key, so it repaints in place and never triggers a relayout. That half is done and correct.

Read §15's sentence again: *the tree tab carries a live-run mark, **or nodes appear with no
explanation** and it reads as a bug.* A pulsing node with nothing saying why **is** the bug it
names. What is missing is the run-level statement, and that is all this slice adds:

- **A run chip in the top bar**, beside the existing `View-only` badge: *Autopilot · explore ·
  12/140 · q12*, where `q12` is the run's **anchor** — a question id, never an idea id. It is
  present whenever a run reads **running** (§I-0), on **every** tab, and clicking it switches to
  the Autopilot tab. The top bar is outside the SVG, so no tree render can drop it and no tree
  render is needed to draw it.
- **A ring on the anchor question** in the tree, so the pulsing attempts are visibly children of
  something identified. This is a class toggle on an element that already exists — spec 12's
  structural-vs-cosmetic rule — applied by one function called both from the `/auto.json` poll and
  at the end of `renderTree()`, because the anchor's run state is not in `treeSignatures`' key and
  a structural render would otherwise drop it. It **never calls `renderTree()` itself**.

Both come from the `/auto.json` poll, which runs **whatever tab is up** — one small ETag'd request
that answers 304 forever on an idle vault.

**Rejected: a second per-node mark for in-flight attempts.** Two "running" indicators, one from
node status and one from `state["in_flight"]`, would disagree in the window between a phase change
and the node write — and the one that is already there is the one the tree's own diff is built to
repaint. **Rejected: a new per-node snapshot field.** It would have to join both
`treeSignatures`' cosmetic key and the `NOT_RENDERED` field-coverage guard
([selftest.py:4260](../../skills/crux/scaffold/selftest.py)), and it would put run state back
inside the snapshot this slice is keeping it out of.

### J · Purity and the import floor

`auto_cockpit` and `auto_portfolio` are pure functions in `engine.py`: they read files, which the
engine already does, and they start no process, touch no git and start no thread. Nothing new goes
in `autopilot.py`. `serve.py` gains **no new import** — `json`, `os` and `hashlib` are already in
its allow-list at [selftest.py:1156](../../skills/crux/scaffold/selftest.py), and the criteria
assert that list is unchanged.

## Scope — what this does not do

- **No writes.** The cockpit stays read-only; there is no button that starts, pauses, stops or
  approves a run. Those stay in the CLI, and the existing read-only footer covers the tab.
- **No live-updating animation** beyond what the 1 Hz poll already redraws, and no re-render on an
  unchanged payload — the same two-tier diff discipline the tree and taskhub already keep.
- **No new agent, no engine bump, no migration, no new plan field.**
- **The spec's three open questions stay open** — the steward's value, the migration rate, whether
  two concurrent runs matter. This tab displays whatever is on disk; it answers none of them.
- **Spec §8's run-branch commits stay deferred** (PI, 2026-09-18). Not adopted here.
- **05.3's accepted suite-growth overage is not revisited.**

## Acceptance criteria

Each is a command with an expected result, and each becomes a selftest assertion.

**The endpoint**

- [ ] `engine.auto_cockpit(root)` on a vault with no `auto/` directory returns
      `{"active": false, "runs": []}` and creates nothing — asserted by comparing a full
      directory listing before and after.
- [ ] `engine.auto_cockpit(root)` on a vault with one run returns `active: true` and exactly one
      run whose keys are a pinned literal tuple, asserted as a tuple and not a length.
- [ ] `auto_cockpit` returns a complete payload **while `engine.Vault` is monkeypatched to raise** —
      the proof that the endpoint never reads the tree.
- [ ] Every attempt row's `score`, `island`, `builds_on`, `title` and `verdict` match what
      `auto_island_attempts` reports for the same vault, for a tier-0 run — the ledger-derived
      view and the tree-derived one agree.
- [ ] `GET /auto.json` returns 200 with an ETag; an immediate repeat with `If-None-Match` returns
      304 with no body; a ledger append changes the ETag.
- [ ] `GET /auto.json?events=1` returns one ledger event and the true total; `?events=99999` is
      capped at 2000; a non-integer value is treated as absent, never as an error.
- [ ] `serve.py`'s import line is unchanged, so the local stdlib-only check in `run_serve`
      ([selftest.py:1147](../../skills/crux/scaffold/selftest.py)) passes untouched.
- [ ] `/auto.json` takes **no path segment and no id** — it enumerates `auto/` itself and carries
      every run — so it has no traversal surface at all; its only query parameter is an integer.
      Asserted by the `/wiki/` route's own `builtins.open` spy pattern: no file outside
      `auto/<qid>/` is opened.

**The snapshot stays out of it**

- [ ] `engine.snapshot`'s top-level key set is still exactly the eleven names
      [selftest.py:543](../../skills/crux/scaffold/selftest.py) pins — no `auto` key is added.
- [ ] Appending a byte to `auto/<qid>/ledger.jsonl` does **not** change `serve.vault_stat_key`;
      touching a node file does.
- [ ] A full tier-0 search leaves `engine.snapshot(root)` byte-identical to what it was before
      `auto/` was written to, modulo the attempt nodes the run legitimately filed — asserted by
      running the snapshot twice around a pure ledger write.

**The portfolio**

- [ ] `auto_portfolio` on a chain of five attempts where each builds on the last returns exactly
      one row — every other candidate is an ancestor or descendant of the best.
- [ ] `auto_portfolio` on five unrelated attempts returns five, ranked by the objective's
      `direction`; with `direction: max` the largest is first and with `min` the smallest is.
- [ ] An `invalid-run` attempt never appears in the portfolio, and a `None` score never outranks a
      real one.

**The frontend**

- [ ] `index.html` carries a fourth `[data-tab]` button, `auto`, and an `#auto-pane` with
      `#auto-rail` / `#auto-rail-body` / `#auto-body`, matching the Taskhub's structure.
- [ ] The exact-set tab assertion at
      [selftest.py:4712](../../skills/crux/scaffold/selftest.py) reads
      `{"tree", "wiki", "tasks", "auto"}` and still passes — its scanner is
      `data-tab="([a-z]+)"`, so the id is lowercase letters only.
- [ ] The Autopilot rail's click listener is attached to `#auto-pane`, not `#tabs`, asserted by a
      static source check — the Taskhub's own repair note records that the other choice left its
      rail dead.
- [ ] `AUTO_VIEWS` in `app.js` is exactly `[["live","Live"],["results","Results"]]`, asserted by a
      static read of the source, so the rail and this PRD cannot drift.
- [ ] The Autopilot tab is hidden when `auto.json` reports `active: false`, and the active tab
      falls back to Tree when a run's directory disappears — the same two lines `updateTabs`
      already runs for Wiki and Taskhub.
- [ ] No `renderTree()` call appears in the live-mark code path, asserted by a static source check
      over the function that applies the mark; the function is called from both the poll and the
      tail of `renderTree()`.
- [ ] `nodeSVG`'s `running` class and `treeSignatures`' cosmetic key are **byte-identical** to
      their pre-slice values — no second per-node mark is introduced.
- [ ] `engine.snapshot` gains no new per-node field, so `NOT_RENDERED`
      ([selftest.py:4260](../../skills/crux/scaffold/selftest.py)) is unchanged.
- [ ] `app.js` loads no new script and `index.html` references no new vendor file.

**Behaviour after the stop**

- [ ] With `state["stop"]` set, the Live view still renders the full history and shows the stop's
      `reason` and `detail` verbatim; it does not blank, and it does not switch views by itself.
- [ ] A **stale** run says so and names the last write's timestamp; it never renders as running and
      never claims the driver died.
- [ ] The run chip is present while the run reads **running**, on every tab, and absent once the
      run reads **stale** or **stopped**; the anchor ring follows it.
- [ ] `auto_cockpit` reports `liveness: "running" | "stale" | "stopped"` by the §I-0 rule, asserted
      at all three by moving `updated` and setting `stop`; the threshold is a named constant.

**The house gates**

- [ ] `./crux selftest` is `ALL GREEN` at every pushed commit.
- [ ] All **eight** CI jobs pass, Windows included — the Windows job's own comment names the

- [ ] A vault created before this work loads unchanged, with no drift warning.
- [ ] Suite growth is budgeted and measured: this slice's new sections are reported in seconds

## Backward-compat / migration

None. No engine bump, no vault-format change, no new plan field, no change to any existing
endpoint's payload or key set. A vault with no `auto/` directory is untouched and its cockpit is
identical. The one behaviour change to existing code is `vault_stat_key` skipping `auto/`, which
can only make the snapshot cache **hit more often** and cannot change the snapshot's content,
because `engine.snapshot` reads nothing there.

## Build notes

- `engine.py` stays pure: no process, no git, no threads. `serve.py` gains a route and a cache
  triple; `autopilot.py` is not touched at all.
- The Purity grep's ban on the quoted literal `"commit"` is an `autopilot.py` rule; this slice does
  not edit that file. The `node-filed` ledger record's field is `builds_on`, not `commit`.
- Any edit to `skills/crux/SKILL.md` re-pins the five `persona-01` fixtures in the same chunk. This
  slice should need no such edit; if a chunk finds it does, that is a stop, not a workaround.
- One check fails in every git worktree and nowhere else
  (`doctor: a roster short of the repo's warns — a stale install.sh`). A builder's expected state
  is `PASSED N-1 / N`. Not theirs to fix.
- New selftest checks take the prefix **`autogui:`**, following the file's one-prefix-per-subsystem
  convention (`serve:`, `webui:`, `file:`, `wiki-gui:`, `taskgui:`, `apure:`).
- Route tests run against a **real** `ThreadingHTTPServer` on a free port with `urllib.request`,
  the pattern `run_serve` and the wiki-route tests already use — not by calling handler functions.
- Two existing exact-set assertions must be updated in the same commit as the code that trips them:
  the tab list ([selftest.py:4712](../../skills/crux/scaffold/selftest.py)) and — only if a
  snapshot key were ever added, which this slice does not do — the top-level key set
  ([selftest.py:542](../../skills/crux/scaffold/selftest.py)).
- `CHANGELOG.md` gains one entry, newest-first under `## [Unreleased]`.
- Windows: the new route is a pure `json`/`os.path` path with no filesystem traversal of its own —
  it reads three fixed filenames — but the cockpit's routes are the informational job's stated blind
  spot, so the route's test must run on a real server, as the wiki route's already does.
