# PRD: 05.3 — the agents

- **Kind:** feature
- **Spec:** [.spec/05-autopilot.md](../../.spec/05-autopilot.md) — 05.x series, after [05.2](05.2-driver-loop.md)
- **Signed off 2026-09-17** by the PI, with the fifth act **ruled in**: inside an approved Explore
  run the plan's approval covers `ask` — the steward opening one new island under the anchor, up to
  the signed `island_cap` — as a fifth act beside the four 05.2 named. §H carries the sentence that
  goes into `skills/crux/SKILL.md`.
- **Amended 2026-09-17** by the foreman, against the spec and the 05.2 code on disk: `agent_failover:`
  is built rather than read (it is a name in one constant with no consumers, as are the un-coerced
  `steward_every:` and `island_cap:`); the probe's removal rule gained the clause that drops a
  dangling flag; the rate-limit patterns are attributed to the `era` skill's MIT `generate.py`, not
  to Apache-2.0; the leash insertion is sentence-for-sentence because the second anchor is
  soft-wrapped; the doctor-roster build note named a check that pins nothing; `flight_plan_hash`
  already excludes the content of `## Guidance`; the brief has five checks, not six; the close brief
  adds to `crux-close`'s table rather than replacing it; `closer:` defaults false to keep a 05.2
  plan running unchanged; the cooldown wait re-evaluates `auto_stop` on every poll; and
  `worker-start` now means the whole list failed and aborts rather than retrying.

## Problem / motivation

05.2 built the loop. It runs end to end against a stub: a script stands in for the agent, the
driver grades every check by arithmetic, and the findings come from a fixed template. **This PRD
puts the three model-calling roles of §5 and §6 into that loop** — the worker that drafts an
attempt, `crux-close` that reads the output, and the steward that watches a stalled search — and
it builds the one piece of machinery all three need: a command that can be named, probed before
the spend, and walked past when a provider refuses.

Three things stop being deferred here.

- **The agent command is a template with failover (D18).** §11 says a provider rate limit must
  never cost a night. Today one `agent:` line is run as written, and a limit hit at midnight ends
  the run.
- **`auto check` can prove the agent is reachable.** That is the third clause of the epic's
  acceptance line, and the two scorer clauses shipped in 05.1. A plan whose agent command is
  misspelled currently fails at attempt one of a hundred and forty.
- **Prose checks come back.** 05.2 refuses any plan check that is not a metric comparison,
  because the driver has no reader. `crux-close` is that reader, and it has existed, unchanged,
  since spec 09.

The four reused agents stay byte-identical. Where `crux-close`'s written output does not fit a
machine reader, the fix is a new seam — the brief the driver hands it — never an edit to its
definition.

## Design decision

### A · Two agent definitions, and the rule that a headless agent has no voice

`agents/crux-auto-worker/AGENT.md` and `agents/crux-auto-steward/AGENT.md` are written in the
shape the other ten use: frontmatter (`name`, `description`, `cold_input`, `toolbelt`,
`excludes`, `license`, `metadata`) and a body of *when invoked · rules · output*. They join the
roster `crux doctor` counts.

**The worker** reads one thing: the brief at `CRUX_BRIEF`, which 05.0 assembles and which already
carries the plan's `## Guidance`. It writes exactly two things: a commit in its own worktree, and
one JSON object at `CRUX_PROPOSAL`. It runs the plan's run command (`CRUX_RUN`) itself; the driver
never does. It never runs the scorer, never writes the vault, never leaves its worktree and
workspace, and never names a verdict. Its claim must fit `PROSE_CAP` — 400 words — because an
over-cap claim is refused and retried, never truncated. Its proposal schema is closed and is
printed in the body verbatim: `claim`, and optional `controls` of `{text, fails_if}`, each a
metric comparison with its own failure scenario. It may add outcome-neutral controls and nothing
else (D17), which holds by construction rather than by instruction: there is no field in which a
claim-directed check can be written.

**The steward** reads the run brief of section H and writes one proposal. It may propose standing
guidance for later workers, or one new island; nothing else, and never a vault write.

**The vocabulary rule, stated once for both.** A worker is headless. It never talks to the PI, so
spec 16's invisible-notebook rule — never say an id or a crux word in chat — **does not apply
inside it**. Node ids, `verifiable`, `island`, `invalid-run` are its working language, and writing
the body in a private dialect would cost clarity for no gain. What does bind: **nothing a worker
or a steward emits ever reaches PI chat unmediated.** Its claim reaches the PI as a node's
`## Idea / Hypothesis`, its log stays in its workspace, and its proposal is read by the driver
alone. So `voice_lint` is never pointed at these two agents, and the two bodies say so, in a
sentence, so nobody adds it later by analogy.

**Rejected: one agent definition with a mode switch.** Rule 2 of spec 09 is one job per agent, the
two inputs share no field, and a mode flag is how a steward starts writing code.

### B · The command list, and the walk

`agent:` is required, parsed and run today. **`agent_failover:` is not** — it exists only as a name
inside `AUTO_LIST_FIELDS`, a constant with zero references anywhere in `engine.py`, `autopilot.py`,
`crux.py` or `selftest.py`: it is never split, never type-checked, and never reaches the driver's
plan dict. So this slice **builds** that field rather than reading one that works, splitting it with
the same `_csv_field` that already splits `islands`, `frozen` and `writable`, and type-checking it
like them. (`steward_every:` and `island_cap:` are in the same half-built state — required and
int-checked, but never coerced into the plan dict by `load_flight_plan`; the steward needs both, so
this slice coerces them too.)

The two become one ordered **command list**: `[agent] + agent_failover`, first entry preferred. Nothing
about how a command is run changes — `shlex.split`, no shell, `cwd` the worktree, stdin
`/dev/null`, output to `worker.log` — and two substitutions are made in any argv element:
`{brief}` as today, and `{agent}`, the name of the role being invoked
(`crux-auto-worker` · `crux-close` · `crux-auto-steward`). The same name goes into the environment
as `CRUX_AGENT`, so a template can route either way:
`claude -p --agent {agent} "{brief}"`. The worker's seven variables of 05.2 are unchanged and
`CRUX_AGENT` is the eighth.

**One try walks the list once.** A command that cannot start — it does not parse under `shlex`, it
is empty, or the kernel refuses it — is not an answer about the model; it is an answer about the
machine. The driver logs `failover`, moves to the next command and starts there. Within one try
each command is attempted at most once.

**A failover is not a retry, and it is not a model call.** 05.2 charges `budget_model_calls` at
the top of every worker try; that charge moves to the moment a child is actually spawned, because
a command that never became a process cannot have spent a token. `retries` is untouched by a
failover: it counts tries, and a walk is one try over several commands. So a night of eight
failovers costs the budget nothing, which is the whole point of having a list.

**When every command in the list fails to start, the run stops `abort`**, with a pinned detail
naming each command and why it could not start; the in-flight attempt is abandoned by the stop
path as in 05.2 (reason `stop`) and no node is filed. Waiting cannot fix a misspelling, and the
same fault at run open is caught earlier still by section D. (05.2 retried a `worker-start`
failure like a crash; with a list, one try already walked every command, so there is nothing
left to retry.) `worker-start` therefore stays in `AUTO_WORKER_RETRY_REASONS` but changes meaning:
it is now raised only when the **whole list** failed to start, and it stops `abort` instead of
retrying. The constant is not edited; the one call site that raised it per-command no longer exists.

**Rejected: a failover that charges a retry.** Two entries in the list would then halve the
retries the PI asked for, which is an interaction nobody would predict from the plan.

### C · The rate-limit signal is the log tail, and a cooldown, and a wait

A provider limit looks nothing like a crash: the command usually starts, says so in words, and
exits. §11 asks for a failover with a cooldown and a re-probe, which is what ERA's `generate.py`
already does — a closed list of case-insensitive patterns over the child's output, a cooldown
window, then a probe of the preferred backend. The arithmetic is ported with attribution, not
imported; crux vendors nothing.

- **What counts as a rate limit:** the tail of that try's `worker.log` matches one of
  `AUTO_RATE_LIMIT_PATTERNS`, a closed list in `engine.py` ported verbatim from the `era` skill's
  `scaffold/generate.py` `LIMIT_PATTERNS`. **The attribution comment names MIT, not Apache-2.0**:
  `generate.py` carries no licence header and is part of the PI's own MIT-licensed `era` skill.
  Apache-2.0 and FROZEN belong to `futs.py` alone, which is the separate file 05.0 ported the PUCT
  arithmetic from — writing Apache-2.0 here would attribute a licence the source does not carry.
  Seven case-insensitive regexes: `5-?hour limit` · `usage limit` · `rate limit` · `limit reached` ·
  `too many requests` · `reset[s]? at` · `please try again later`; read by one pure function
  `auto_rate_limited(text)`.
- **When it is read:** only after a try that already failed — a non-zero exit, no commit, or no
  usable proposal. **A successful try's log is never scanned.** An agent that merely mentions a
  rate limit in a transcript it then commits over must not be able to move the driver.
- **What happens:** the command goes on cooldown until `now + agent_cooldown` (a new optional plan
  field, seconds, default 1800), recorded in `state.json` as an absolute wall-clock time so a
  resume does not forget it, and the try re-runs on the next command that is not cooling. The
  ledger carries `cooldown` then `failover`.
- **The re-probe is free.** Every try starts at the head of the list and skips only what is still
  cooling, so the preferred command comes back by itself the moment its window lapses. There is
  no probe schedule to get wrong.
- **When every command is cooling, the driver waits** for the earliest expiry, polling its
  in-flight workers as usual, and then walks again. It does not abort: a rolling limit is the
  interruption this feature exists to survive. The wait is charged to `budget_hours` like any
  other driver time, and **`auto_stop` is re-evaluated on every poll of that wait**, not only
  between attempts — otherwise a thirty-minute cooldown under a one-minute budget overruns by
  twenty-nine. So a night lost entirely to limits ends on the `budget` stop rather than running
  forever.

**Rejected: an exit code as the signal.** No two agent CLIs agree on one, so pinning a number is a
guess that fails silently. **Rejected: a sentinel file the worker writes.** The worker being
refused service is exactly the one that never got far enough to write a file.

### D · Reachability in `auto check` — the probe, and what it is allowed to cost

`crux auto check` gains a third block beside `repo` and `scorer`: `agents`, one row per command in
the list, each carrying the command, the probe argv, `reachable`, the seconds it took and a detail.

**The probe is the command with the placeholders taken out, plus the arguments of `agent_probe`**
(a new optional plan field, default `--version`), run in the repository with a short timeout
(`agent_probe_timeout`, default 20 s) and stdin `/dev/null`. The removal rule has **two clauses**,
and the second is not cosmetic — without it the flag that introduced a placeholder is left
dangling and the probe is malformed:

1. drop every argv element containing `{brief}` or `{agent}`;
2. then drop a trailing element that begins with `--`, if dropping clause 1 left it as the last
   element and it was immediately followed by one of the elements clause 1 removed. **`--`, not a
   single `-`** — a single dash would eat the `-p` in the second example below, which is a flag
   that takes no value and must survive.

So `claude -p --agent {agent} "{brief}"` loses `{agent}` and `{brief}` by clause 1 and the now
dangling `--agent` by clause 2, probing as `claude -p --version`. The shipped template's
`claude -p "{brief}"` loses `{brief}` by clause 1 and keeps `-p`, which clause 2 does not match,
probing as `claude -p --version` too. 05.2's tier-0 stub `python3 agent.py step` — which
carries no placeholder and reads `CRUX_BRIEF` from the environment — is untouched by both clauses
and probes as `python3 agent.py step --version`. Dropping only what the substitution owns is what
makes the probe prove the *agent*, not merely the interpreter, and it sends no prompt, so it spends
no model call.

**Reachable means the program started and exited inside the timeout — the exit code is not read.**
Not every CLI answers `--version`, and refusing a plan over that is a check about a flag rather
than about the agent.

Two problem slugs, and one is static: `agent-command` for a command that does not parse or is
empty (reported by `flight_plan_problems`, so `auto check --static` catches it with no process);
`agent-reach` when **no** command in the list is reachable, which is the spec's acceptance line
word for word. One unreachable entry beside a reachable one is reported in the `agents` block with
`reachable: false` and is **not** a problem — a failover list is allowed to name a CLI this
machine does not have.

`--static` stays the no-process path and its output is **byte-unchanged**: 05.1 pins its key set
exactly (`ok, plan, anchor, mode, problems`), so there is no `agents` key at all, and
`agent-command` lands in `problems` like any other static slug. Only the non-static result gains
`agents` (05.1 pins that key set as a superset, so it holds).
`auto run` runs the same probe once at run open, in the same place the base-commit scorer check
already sits, and stops `abort` before reserving any id when none is reachable.

**Rejected: probing argv[0] alone.** It proves an interpreter exists and says nothing about the
agent behind it, which is the failure the check is for.

### E · `crux-close` wired in, unchanged — the brief carries the schema

`agents/crux-close/AGENT.md` is byte-unchanged, and so are `crux-null`, `crux-verifiables` and
`crux-design`. Its written output is a table for a human, which no driver can parse; the fix is a
seam, not an edit. **The instruction that turns its answer into a file lives in the close brief**,
which the engine assembles and the driver hands over — the same channel the worker's brief uses,
and the same principle spec 09 settled: the engine builds the brief, so no calling agent authors a
sentence of it. Writing a proposal into a scratch workspace is exactly the act `crux-close`'s own
definition already names as its deliverable, and it still never runs `crux close` and never
touches the vault.

Opt-in, by a new optional plan field `closer: true` (**default false**). The default is false and
not true, even though spec §6 puts `crux-close` in the lifecycle unconditionally, for one reason
that is a criterion below: *a 05.2 flight plan runs and closes exactly as before*. A plan written
before this release carries no `closer:` field, and defaulting it on would make a run already in
flight start spawning a fourth process and spending `budget_model_calls` its PI never budgeted.
The spec's lifecycle becomes the default in practice at **05.5**, where the setup skill writes
`closer: true` into every new plan; that is stated here so the default is a deferral rather than a
disagreement with the spec.

**The close brief adds to `crux-close`'s output; it does not replace it.** That agent's own
`## Output` section ends *"A table of (verifiable, proposed tick, the evidence), the
outcome-neutral result, and the findings draft. Then stop."* — and it stays byte-identical. So the
brief's instruction is worded as an addition (*"…and also write that same proposal as one JSON
object to `$CRUX_PROPOSAL`"*), never as a substitution, because two instructions in one context
that contradict each other are how a model ends up doing neither. Pinned as a criterion: the brief
contains no sentence telling the agent not to print its table.

With `closer: true` set:

- After scoring and before `cmd_close`, the driver invokes the same command list with
  `CRUX_AGENT=crux-close`, `CRUX_ATTEMPT`, `CRUX_WORKSPACE`, `CRUX_BRIEF`, `CRUX_PROPOSAL`
  (`<workspace>/close.json`) and `CRUX_RESULTS` (the absolute path of `results/<hid>/`). It is
  a model call and is charged as one; it is retried on a failure to start, under the same
  `retries`, and it walks and cools exactly as section B and C say.
- The closer is awaited **synchronously** inside the post-worker pipeline, one attempt at a time,
  exactly where scoring already blocks; in-flight workers keep running and are polled once it
  returns. **No phase is added to `AUTO_PHASES`** — the crash fixture iterates that tuple — so
  the closer runs inside phase `closed`, and a kill during it resumes through 05.2's R2: the
  metrics are on disk, S9 runs again, and the closer is invoked (and charged) again.
- Worker-added controls stay metric comparisons whatever `closer:` says — `auto_proposal` is
  unchanged. Only the plan's own checks may be prose, and only the closer grades them.
- The close brief is engine-assembled, byte-stable, and carries: the node's checks with their
  kinds and the combination rule, which of them the engine has already graded and how, the
  results directory, the closed proposal schema, and the findings cap. It carries no verdict and
  no advocacy — the anchor's `## Problem Statement` is excluded, as everywhere else.
- **05.2's `check-grammar` is lifted when `closer: true`** and is unchanged otherwise. So a plan
  with no closer still cannot make `supported` unreachable, and every existing fixture's problem
  list stays byte-identical.

The proposal schema is closed: `ticks`, an object keyed by check index (1-based, plan order, which
is node order) with values from the alphabet `x` · ` ` · `-`; `findings`, the paragraph; and
`report`, the markdown of section G. Any other key, any other tick value, or an index naming no
check refuses the whole proposal. There is no `verdict` field, so no verdict token can arrive from
a model, and 05.2's static scan — no verdict token assigned anywhere in `autopilot.py` — still
passes.

**Rejected: editing `crux-close` to emit JSON.** The four reused agents are fixed by the handoff's
non-negotiables, and an agent whose output format is owned by one caller stops being reusable.

### F · The engine still grades what it can, and a contradiction is refused

The tick vector is **merged, not replaced**. For every check that is a metric comparison, 05.2's
grading stands: the engine reads the number and ticks it. The closer's ticks fill the rest — the
prose checks, which is the reason it is here.

**A proposed tick that disagrees with a graded comparison refuses the whole proposal**, unretried,
because it is the agent's act rather than the machine's and the same agent would repeat it. A
proposed tick that agrees is ignored, not applied — the engine's is already there. That makes a
disagreement a cheap, recorded signal about the agent rather than a silent overwrite of a number.

**What a closer failure does — and what it must not do.** Unreachable after the walk, retries
exhausted, malformed, contradicting, or findings over the cap: in every case the attempt closes on
**the engine's own vector**, with `[-]` on every check the engine could not grade, and with 05.2's
fixed-template findings. The ledger carries one `closer` event saying `ok: false` and why.

It is deliberately **not** `invalid-run`. The closer is a reporter, not a measurement: the run
happened, the scorer's document is on disk, and calling the attempt invalid because a reporting
agent failed would throw away real evidence — and would let a flaky provider manufacture a streak
of invalid runs that trips the `abort` stop. The honest consequence is stated rather than hidden:
a prose check left at `[-]` on an outcome-neutral control is `invalid-run` under
`derive_verdict_15`, which is correct, because the control genuinely could not be evaluated.

`cmd_close` and `derive_verdict_15` are untouched, as in 05.2. The driver supplies ticks and never
a verdict.

**Rejected: letting the closer overrule a graded comparison.** The number is the frozen scorer's,
which is the guardrail §10 is built on; a model that can retick it can grade its own homework.

### G · The report under `## Artifacts`, with or without a closer

05.2's scope note left `validate` reporting "files but no report is linked" on every attempt node.
Over a hundred and forty attempts that is a hundred and forty problems the loop manufactured
itself. This slice closes it: the driver writes `results/<hid>/report.md` and links it as
`- [Report](results/<hid>/report.md)` under the node's `## Artifacts`, inside the same lock hold
as the close and before `cmd_close` runs.

With a closer, the report is the closer's `report` prose, capped in bytes. With no closer, it is a
fixed template — the objective and its value, the tick table with each found number, the failure
that closed an invalid run — the same material the findings paragraph already states. Either way
the file is the driver's write, from text a model supplied; the agent never touches the vault. The
report lives under `results/`, so it does not count against `PROSE_CAP`; the findings paragraph
sits in the node body and does.

**Rejected: linking the metrics file as the report.** `ARTIFACT_KINDS` maps a report to `.md`, and
a JSON document is data, not a reading of it.

### H · The steward: when it runs, what it sees, what it may propose

05.2 refuses `steward: true`; this slice accepts it. The steward is fresh every time, sees no
conversation, and lives minutes (§5).

**When.** Explore only, and only with the switch on. It runs when `steward_requested` is set —
which is what 05.2's single stall escalation does in Explore — and otherwise every
`steward_every` closed attempts. Never two at once, and never twice inside one `steward_every`
window, so a stall landing just after a periodic run does not pay twice. On a Climb plan the
switch is legal and the steward simply never runs: a run may be moved from Climb to Explore
mid-flight (§2), so the switch being on is not a mistake to refuse.

It is a model call, charged to `budget_model_calls` like a worker try, and it is not started when
that axis is spent. It is spawned through `_spawn` and registered beside the workers, so it never
outlives the driver, and it is polled with them: it blocks nothing, its proposal is applied when
it exits, and a brief assembled while it runs simply predates its advice.

**What it sees.** A steward brief the engine assembles, byte-stable, from the run's own record:
the goal, the objective and its direction, the island table (each island's question title, best
score, stall counter and attempts), the tail of the ledger under a per-section budget, the
guidance in force, and the budget remaining on every axis. **The five brief checks of
`AUTO_BRIEF_CHECKS` apply here too** — `schema`, `budget`, `stable`, `leakage`, `addresses` — over
the steward's own slot list and its own budget keys. (Spec §13 counts six; the sixth is the
`--lint` verb, not a check in the tuple. The engine has five, and the steward gets the same five.) Excluded and asserted: the anchor's `## Problem Statement`, any attempt's
diff or code, and any findings prose. §5 says "the ledger only"; this is the ledger plus the facts
without which no proposal about islands could be written, and the exclusion list is the part that
was load-bearing.

**What it may propose.** A closed schema, `{guidance?, island?}`, at most one of each:

- **`guidance`** — standing text for later workers. The worker brief therefore gains one new
  section, and its two constants are pinned here so no builder invents them: a budget key beside
  `AUTO_BRIEF_BUDGET`'s existing `{"inspirations": 3, "refuted": 5, "guidance": 10,
  "findings_words": 80}`, holding the same **10** lines under the same cut rule; and an empty-case
  string beside `AUTO_NO_GUIDANCE`, so a brief with no steward advice says so out loud rather than
  rendering a blank, exactly as every other empty section already does. It is recorded in
  `state.json`, attributed to
  `crux-auto-steward` and stamped, and every later brief carries it in its **own labelled
  section**, separate from the PI's. **The plan's `## Guidance` is not written.** The reason is the
  leash and only the leash: `auto guide` is the PI's verb (◆) and the plan document stays theirs
  alone. It is *not* a hash argument — `flight_plan_hash` already removes the **content** of
  `## Guidance` from what the PI signed, and says so in its own docstring, so appending there would
  not clear an approval. The steward is kept out because the verb is the PI's, not because the hash
  would notice. A worker therefore sees who said what.
- **`island`** — one new sub-question under the anchor, `{title, problem}`, refused once the
  island count reaches `island_cap`. Safe for the reason D14 gives: the objective, bar and checks
  are frozen, so a new island is another angle on a fixed target. The new island is recorded in
  `state.json`'s island table; the plan's `islands:` frontmatter is **not** edited, because that
  field is hashed and writing it would clear the PI's approval mid-run. From this slice the
  island table the loop consults — the round-robin, `auto_brief(island=)`,
  `auto_island_attempts` — is `state.json`'s, seeded from `islands:` at run open. Applying an
  island proposal files the sub-question under the anchor with `cmd_ask` and cuts its branch at
  `base`, exactly as `open_run` cuts the plan's islands.

Anything else is unreachable by construction: two keys, so there is no field in which an
objective, a bar, a check, a null, a budget or a merge can be expressed. A proposal carrying
another key is refused, logged, and the run carries on. A steward that cannot start, fails, or
returns nothing is logged and the run carries on — **a steward never stops a run**, because it is
advice and a run that dies for want of advice is worse than a run without it.

**One thing this does not settle.** Whether the steward earns its place at all is a spec open
question, answerable only with evidence from a real run. This PRD defines the mechanism and leaves
the question open on purpose; the switch ships off by default, and 05.6 is where the evidence
comes from.

**The fifth act — RULED IN (PI, 2026-09-17).** Filing a question is `ask`, which the leash marks ◆,
and 05.2's ruling in `skills/crux/SKILL.md` names **four** acts the plan's approval covers —
`hypothesize`, `approve-null`, `test --to running`, `close`. Opening an island is a fifth. Spec D14
already settles that the loop may open islands up to the cap, and `island_cap` is a required field
the PI signs in every plan, so ruling it out would have shipped a spec and a leash that contradict
each other. The PI ruled it **in** at this PRD's sign-off. The island half therefore applies as
described above — there is no refuse-at-apply path and no second build.

**The leash edit.** One sentence is inserted into the leash paragraph after *"…inherited by every
attempt."* and before *"Outside an approved autopilot run, nothing changes."* — **the second anchor
is soft-wrapped in the file** (the bytes are `Outside an` · newline · `approved autopilot run,
nothing changes.`), so the edit re-wraps the paragraph and byte-identity holds
sentence-for-sentence, not line-for-line. The sentence, verbatim:

> In Explore, the approval also covers a fifth act that is not per attempt: `ask` — opening one
> new island (a sub-question under the anchor) when the steward proposes it, up to the plan's
> `island_cap`, which the PI signed. It is safe for the reason spec 05 D14 gives: the objective,
> bar and checks are frozen, so a new island is another angle on a fixed target.

Because `SKILL.md` now certainly changes, the five `persona-01` fixtures are re-pinned in the
**same chunk** — this is no longer conditional.

**Rejected: appending the steward's text to the plan's `## Guidance`.** It is the PI's document
and their signed verb; a labelled section in the brief gives the worker the same words with the
author attached. **Rejected: per-island guidance sections in the plan.** A new plan format, for a
distinction the brief already carries — each worker is told which island it is on.

### I · Eval fixtures, and what tier 0 proves with no model

Two fixtures in the shape spec 10 pins — `evals/fixtures/<name>/{PLANTED.md, vault/,
submissions/}`, hand-authored, `band: unset`, `k: 5`, `agent_sha` pinned to the agent's own
`AGENT.md`, with a row each in the proxy register that `selftest` cross-checks against the
manifest.

- **`worker-01`** — a brief whose island has one refuted sibling with a written failure scenario,
  and a planted key: the claim must move the parameter the scenario names, the proposal must carry
  a control that is a metric comparison, and no claim-directed check. The hard half is engine
  graded: `auto_proposal` validates the submitted proposal exactly as the driver would. The soft
  half — is the claim any good — is a stated key, so the fixture is a **proxy** and says so.
- **`steward-01`** — a ledger in which one island has stalled and another is starving, with the
  correct proposal known by construction. Hard half: `auto_steward_proposal` validates the
  submission. Soft half: which island the guidance names. **Proxy.**

`close-01` is unchanged: `crux-close` is unchanged, and its fixture already grades the tick vector
against `derive_verdict_15`.

**Tier 0, in selftest, with no model.** Every criterion below is an assertion over the 05.2 tier-0
fixture, extended with stub scripts only: a stub agent that cannot start; one that prints a
rate-limit line and exits non-zero; one that prints a rate-limit line and commits anyway; a stub
closer that writes a valid proposal, a malformed one, and one contradicting a graded tick; a stub
steward that proposes an island, proposes guidance, and returns a key outside the schema. Cooldowns
in the fixtures are tenths of a second. **The suite grows by no more than 25 seconds**: it is
46 s in the main checkout today, so the whole of `selftest` stays under about 75 seconds.

**Tier 1 is the manual check, not a criterion.** The California Housing regression in
`~/.claude/skills/era/scaffold/examples/regression/` is where a real agent first runs: a flight
plan in Explore over two islands, `closer: true`, a real `agent:` line with one failover entry,
and a small budget. What is read by hand afterwards: the worker's claims are about the program and
not about the tooling, the closer's ticks match what the results plainly say, the report reads,
and one deliberate mid-run limit (or a stub inserted at the head of the list) shows a `failover`
and a `cooldown` in the ledger and no lost attempt. It is not a selftest criterion because it
needs a model, a network and an attended half-hour.

**Rejected: an eval that applies a proposal and scores the resulting vault.** Spec 10's P3 parks
it — an eval that gives an agent a write path is a leash question, not a harness question.

## Scope — what this does not do

- **No cockpit (05.4).** The new events and the new `state.json` keys are fixed here so the tab
  can read them; nothing is drawn.
- **No setup skill (05.5).** Nothing in this slice writes a flight plan. `closer:`,
  `agent_cooldown:`, `agent_probe:` and `agent_probe_timeout:` are added to
  `templates/flight_plan.md` with their defaults, and the conversation that fills them is 05.5's.
- **No validation on real problems (05.6).** Tier 1 is described as a manual check; tiers 2 and 3
  are 05.6's, and the PI names the tier-3 paper.
- **No change to the four reused agents.** `crux-close`, `crux-null`, `crux-verifiables` and
  `crux-design` are byte-identical, asserted.
- **No leash change beyond the one place.** 05.2 changed it in one place. This slice adds exactly
  one sentence to that same place — the fifth act, ruled in by the PI on 2026-09-17 — and changes
  it nowhere else: the steward writes no plan and no vault section the leash names.
- **No new verdict path.** `derive_verdict_15` and `cmd_close` are untouched; the driver merges
  ticks and supplies them.
- **No commits and no `main`.** Unchanged from 05.2: vault writes stay uncommitted, the loop
  commits on no branch, `main` is never written. 05.2 deferred spec §8's *"every write the loop
  makes lands under the run branch"* on the PI's 2026-09-16 ruling, and this slice defers it
  again — it needs no commits to do its job. **Naming it because no remaining slice owns it:**
  05.4 is the cockpit, 05.5 the setup skill, 05.6 validation. It is the PI's to place.
- **No migration rate between islands.** The brief's migration slot is 05.0's and its rate is a
  spec open question; nothing here tunes it.

## Backward-compat / migration

**No vault format change, so `ENGINE_VERSION` does not bump, and there is no migration.** The
gate's rule is format or verdict/roll-up/view logic. This slice changes none of the three: every
node it files is the ordinary idea node 05.2 files; the `## Artifacts` bullet is ordinary markdown
the section has always held and `parse_artifacts` already reads; `state.json` and `ledger.jsonl`
are not nodes, enter no roll-up and are read by no view; and `derive_verdict_15`, `cmd_close`,
`_verifiables`, `lock_material` and `count_verifiables_by_kind` are byte-unchanged.

Plan fields added, all optional, none touching a vault: `closer:` (bool, default false),
`agent_cooldown:` (seconds, default 1800), `agent_probe:` (default `--version`) and
`agent_probe_timeout:` (default 20). `steward:` and `steward_every:` already exist and are
already validated, and this slice is the first to read them. **`agent_failover:` is a different
case**: it is named in `AUTO_LIST_FIELDS` and nowhere else — never split, never type-checked,
never in the plan dict — so this slice builds it. It is still backward-compatible, because a plan
that omits it gets an empty list and a one-command walk, which is exactly 05.2's behaviour. A plan written for 05.2
validates, runs and closes identically, because `check-grammar` only relaxes when `closer:` is
set and every shipped fixture leaves it unset.

`state.json` gains two pinned keys — `agents` (per-command cooldowns) and `steward` (the guidance
in force, the invocation count and the islands it opened) — so `AUTO_STATE_KEYS` grows from
twenty-four to twenty-six. A `state.json` written by 05.2 is read by 05.3 with both keys
defaulted; the file belongs to a run in progress, not to a vault, and a run that predates this
release resumes rather than breaking.

  builder's expected state is `PASSED N-1 / N`; it passes in the main checkout. That check pins

- **`_spawn` does not register the child; its caller does.** `_spawn(argv, cwd, env, log_path)`
  only opens the log and calls `Popen`; `_worker_try` is what writes `ctx["procs"][hid] = p`, and
  the `finally` in `auto_run` kills what is in that dict. So the closer and the steward each
  register at their own call site — a new spawn that does not is a worker outliving its driver,
  which the handoff names as a defect class. The `auto check` probe is the exception: it is
  synchronous with a timeout and is killed on timeout, and it runs where there is no `ctx`.
- **`load_flight_plan` is where the new fields have to land.** Being in `AUTO_REQUIRED_FIELDS` and
  being type-checked is not the same as reaching the driver: `steward_every` and `island_cap` are
  both validated today and neither is coerced into the plan dict, and `agent_failover` is not even
  in `AUTO_LIST_FIELDS`' consumers. Every field this slice reads — `agent_failover`, `closer`,
  `agent_cooldown`, `agent_probe`, `agent_probe_timeout`, `steward_every`, `island_cap` — gets a
  coercion there, or the driver silently sees a default.
- **`{brief}` substitutes the brief TEXT into argv, not a path** (the path is `CRUX_BRIEF`).
