# PRD: OpenAlex client + DOI enrichment on ingest

- **Kind:** feature · **Spec:** [.spec/17-openalex.md](../../.spec/17-openalex.md) (slice 17.1)

## Problem / motivation

`crux ingest --title` asks the PI to hand-type the paper title plus the full author list,
because the registry title is the vault's only author-bearing field and is what makes a source
findable by author — in `WIKI.md`, in the cockpit's wiki search, and by grep. Hand-typing
produces typos and "He et al", which silently breaks that findability.

A DOI already identifies the work. The canonical string should be fetched, not retyped.

This slice also builds the one network path that 17.2–17.4 all sit on, so every hard
constraint in [spec 17](../../.spec/17-openalex.md) gets solved once, correctly, up front.

## Design decision

A new module, `skills/crux/scaffold/openalex.py`, holding one cached fetcher and three small
pure helpers (work id, title line, DOI → record). `crux.py` imports it **lazily, inside the
one branch that needs it**, so every verb that does not ask for OpenAlex never loads a module
that can reach the network. `cmd_ingest` gains a `workid` argument and takes plain strings.

**The module exists because of spec 05's purity line.** The first cut put the client inside
`engine.py` and tripped `run_auto_purity`, which asserts the engine imports no `urllib` —
the engine is the part a reader has to be able to trust by reading it. That assert was right
and the design was wrong: the client belongs beside `autopilot.py` on the impure side of the
line, importing `engine` and never imported by it. The engine's ingest path stays offline by
construction rather than by convention.

*Rejected:* a provider abstraction with pluggable backends. There is one provider and there
will be one; a wrapper before three call sites is overbuild.

## Scope — what this does not do

No crawl, no ranking, no candidate list, no PDF download, no scoping skill (17.2–17.4 own
those). No new `crux` verb — this is a flag on a verb that already exists. No retraction check
and no SOTA-drift lint. No cache eviction policy: the cache is append-only and small, and a
policy with no observed problem is overbuild.

## The registry format change, and why it is in this slice

17.2 must map a `raw/` file to an OpenAlex work id to use it as a crawl seed, so the id has to
be stored. Storing it in 17.2 instead would mean a second format migration for the same field.

`wiki/.sources.tsv` goes from 4 columns to 5, with the id inserted **before** the title,
because the loader joins everything from column 4 onward into the title. Titles are
whitespace-collapsed on write and so never contain a tab, which makes the column count an
unambiguous format discriminator. A 4-column line loads with an empty id.

## Acceptance criteria

- [x] A 4-column legacy `.sources.tsv` line loads with `workid == ""` and re-saves as 5
      columns with no data loss.
- [x] A `--doi` ingest writes the registry title as `Title — A, B, C (Year)` and stores the
      bare work id, with the network boundary stubbed.
- [x] A second lookup for the same url reads the cache and does not reach the boundary
      (asserted against a stub that raises).
- [x] An explicit `--title` overrides the fetched one; the id is still recorded.
- [x] A plain re-ingest with no `--doi` does not drop a work id already on record.
- [x] With no key and no cache entry, the failure is a `CruxError` naming `OPENALEX_API_KEY`
      and the daily budget — not a traceback and not a hang.
- [x] A non-DOI argument is refused before any lookup.
- [x] `engine.py` imports no `urllib` and never imports `openalex`; `crux.py` imports it
      lazily; `openalex.py` imports `engine` and nothing outside the stdlib.
- [x] `selftest` passes from a fresh clone with `OPENALEX_API_KEY` unset and no network, and
      the assert count has grown (2029 → 2047).
- [x] `crux validate` makes no network call on a vault that holds an OpenAlex cache.
- [x] (manual) One real `--doi` ingest against the live API produces the correct author list.
      Verified 2026-09-19 on `10.1038/nbt.3820` → all six authors, canonical title, year,
      `W2605897695`. The key appears nowhere in the vault, and a re-run with the key unset and
      the network unreachable is served from the cache.

## Backward-compat / migration

**Yes — vault format changes.** `ENGINE_VERSION` 3.3 → 3.4.

Migration is proven against a real old-format vault rather than a synthetic one: the shipped
`skills/crux/examples/demo_vault/` carries a 4-column registry. On a copy, `status`, `validate`
and `review` all pass, `WIKI.md` still renders every title, and the first write rewrites the
file as 5 columns with empty ids and every title intact.

`selftest`'s spec-05.5 version tripwire ("the engine version is unchanged at 3.3") moves to
3.4. It asserts that a version bump is deliberate rather than drifted into; this one is
deliberate, and the comment beside it records which slice moved it and why.

## Security note

The key is read from `OPENALEX_API_KEY` and never written to the vault, which is a git repo.
It is also excluded from the cache key, so a cache is portable between machines and holds no
secret. Both are asserted.
