# PRD: 05.2 — the driver loop

- **Kind:** feature
- **Spec:** [.spec/05-autopilot.md](../../.spec/05-autopilot.md) — 05.x series, after [05.1](05.1-git-and-workspace-layer.md)
- **Amended 2026-09-16/17** with the PI's decisions of 2026-09-16 (the four acts inside a run,
  `crux auto approve`, vault writes uncommitted) and the foreman's fixes (the island-best pointer,
  Explore attempts across questions, non-positive fixture noise, the crash signal on Windows, the
  comparison grammar pinned and the 05.0/05.1 fixtures made comparison-led).

## Problem / motivation

05.0 built the plan the PI signs and the arithmetic that picks what to try next. 05.1 built the
worktree, the ref, the reserved id, the workspace, the manifest and the scorer contract. Both end
at functions nothing calls: a plan that validates and a scorer that runs still produce no attempt.
**This PRD is the loop** — the driver of §5, the one role that lives for the whole run, sees only
vault state, and calls no model.

It is the slice where an attempt first closes, so it carries §12's ruling into
`skills/crux/SKILL.md`, and it is where three invariants stop being promises: a crash closes
`invalid-run` and never `refuted`; a run killed at any point resumes with no attempt lost and none
repeated; `main` is never written. All three are provable here, because the whole search runs
against a stub agent and a stub scorer — tier 0 — in seconds. The engine stays pure (D19): every
process, poll and git call is in `autopilot.py`, and the helpers — the comparison grammar, the
tick vector, the plan's approval hash, budget and stop evaluation — go in `engine.py`, which
still starts no process and names no git command.

## Design decision

### A · Three verbs, and resume is not a flag

`crux auto run <plan> [--max-attempts N] [--json]` is the loop; `crux auto status [<qid>] [--json]`
renders `state.json` and starts no process; `crux auto approve <plan> [--json]` is **the PI's
signature on a flight plan** (◆ — an agent never runs it without the PI's yes). There is no
`--resume`: `auto run` over a vault that already has `auto/<qid>/state.json` reconciles and
continues, because the alternative to resuming is a second run over one run's refs and reserved
ids, and a flag is how that happens at three in the morning. `--max-attempts` only tightens
`budget_attempts`, so a test can bound a fixture.

**Approval is a hash, not a flag.** `auto approve` writes `approved: <now>` and
`approved_hash: "<hash>"` into the plan's frontmatter. The hash covers the plan's text **except**
the content of `## Guidance` and the frontmatter fields `approved`, `approved_hash` and `updated`,
so `crux auto guide` never clears an approval and any other edit does. It is idempotent — the
first approval's timestamp is the record, as with `approve-null` — and it refuses a plan that
`auto check --static` reports a problem on. Approval is **not** a `flight_plan_problems` check (the
05.0 and 05.1 problem lists stay byte-identical) and `auto check`'s output is unchanged; `auto run`
reads it itself.

There is no `auto stop`: §11's four stops are the four stops, an operator's stop file would need a
fifth name the spec does not have, and killing the driver already stops a run that resume then
recovers. `auto run` refuses — **before it writes anything, reserves any id or creates any ref** — a
plan `auto check --static` reports a problem on (which now includes a `replicates:` holding no
integer), a plan with `steward: true` (ignoring a switch the PI approved means the run that
happened is not the run that was signed), a plan that is not approved, and a plan edited after its
approval. It also refuses to continue a run that has already stopped, and a run whose driver is
still alive.

**Rejected: `--resume` required.** It makes the safe path the one the operator has to remember.
**Rejected: approval as a `flight_plan_problems` check.** Every 05.0/05.1 fixture plan is
unapproved, so every pinned problem list would change for a fact that is not a defect of the
document.

### B · The worker writes a commit and a proposal; the driver writes the vault

Per attempt the driver runs the plan's `agent:` command **once** per try, through `shlex.split`, no
shell, `cwd` = the attempt's worktree, `{brief}` in any argv element replaced by the assembled brief
text, and seven variables added to the environment: `CRUX_ATTEMPT` (the reserved id),
`CRUX_WORKSPACE`, `CRUX_WORKTREE`, `CRUX_BRIEF` (a file holding that same text), `CRUX_PROPOSAL`,
`CRUX_SEED` (`0`), and `CRUX_RUN` — the plan's run command, which the worker invokes and the driver
never does. Nothing goes to the worker's stdin (it is `/dev/null`): a command that reads it and a
driver that does not write it deadlock. The worker returns a commit in its worktree and a JSON
object at `CRUX_PROPOSAL` = `<workspace>/proposal.json` — in the **workspace**, not the worktree, so
it cannot land in the commit or reach the next attempt's checkout. Its schema is closed: `claim`,
the prose that becomes the node's `## Idea / Hypothesis`, and optional `controls`, a list of
`{"text", "fails_if"}` objects — added outcome-neutral checks (D17), each a metric comparison with
its own failure scenario.

The **driver** then files the hypothesis, under the lock, at the reserved id, through four engine
acts the plan's approval covers (C and D): `hypothesize` with the plan's null, combination rule and
inherited checks verbatim (claim-directed checks in plan order, then the plan's controls, then each
`controls` entry tagged `[outcome-neutral]` by the driver) and `builds_on:` the parent; then
`approve-null`, `test --to running`, and at the end `close`. The node's title is the claim's first
sentence capped at 15 words; `## Idea / Hypothesis` is the whole claim. So the worker never writes
the vault, writes stay driver-only and serialized, and D17 holds by construction: there is no field
in which a worker can express a claim-directed check. Refusals are in G.

**An Explore attempt whose parent sits under a different question** — the first attempt on island
`qi` builds on the baseline, which sits under the anchor — is filed under its island; `builds_on:`
is written only when the parent sits under the same question and omitted otherwise, because 05.0's
`builds_on` rule refuses a cross-question target. The parent is still recorded, in
`reserved.json` and in the ledger, and the worktree is still cut from the parent's commit (the
baseline's is the run's base). The brief for it is assembled for the island, not for the parent's
question: `auto_brief(root, hid, island=None)` gains an optional island — absent, the island is
`hid`'s parent exactly as in 05.0; given, candidates, inspirations, refuted siblings and migration
are computed for that island.

**Rejected: the worker files its own node.** It puts `_new_id`, `refresh` and the index files
behind an agent — the collision §7 refuses to parallelise — and makes D17 an instruction.

### C · Ticks come from the metrics, by a grammar inside the check text

Nothing in crux turns a metrics address into a tick today: `crux-close` **proposes** ticks for a
human to apply, and `resolve_address` only reads numbers. Without a model this slice defines the
smallest deterministic rule that can. A verifiable whose text — after its `[kind]` tag and any
`(found: …)` note are set aside — **begins** `<key.path> <op> <number>`, separated by whitespace, is
graded from the attempt's metrics:

- `<key.path>` is 05.0's objective-address grammar (non-empty, no `#`, `/` or whitespace) with no
  empty dotted component and no operator character;
- `<op>` is one of `<=` `<` `>=` `>` `==` `!=`, with `≤` `≥` `≠` accepted as spellings of `<=` `>=`
  `!=` (the PI's prose and the 05.0 fixtures already use them);
- `<number>` is any token `float()` accepts that is finite;
- anything after it is free prose.

One pure engine function parses it (`auto_check_comparison`), `metrics_value` evaluates it, and a
ticked line gains the existing `(found: <value>)` note, which `lock_material` already excludes from
the commitment, so neither tick nor note raises drift.

The vector is total: true → `[x]`; false → `[ ]`; **the key does not resolve, or there is no
metrics file at all → `[-]`**. That last case is the whole crash path — a scorer that produced no
document ticks every check `[-]`, and a `[-]` on an outcome-neutral check is already `invalid-run`
under `derive_verdict_15`. The driver asserts nothing.

In this slice **every check in a plan must be a metric comparison**, checked by `auto check` under a
new problem slug `check-grammar` before any spend; prose checks return in 05.3 when `crux-close`
proposes their ticks, and until then a plan carrying one makes `supported` unreachable. The
comparison lives **inside** an ordinary check line, so `_verifiables()`, `verifiable_scenarios()`
and the hash lock are unchanged, and no node written before this release reads differently.

**Rejected: address, operator and threshold as frontmatter fields.** It splits one commitment
across two places, and the hash lock covers only one of them.

### D · The close, and the leash

Per attempt the driver: files the node (`hypothesize` at the reserved id) → `approve-null` on the
plan's null, verbatim → `test --to running`, which takes the hash lock → scores → writes the tick
vector into `## Verifiables` → `close`. The verdict comes from `derive_verdict_15` through the
unchanged close path; the driver supplies ticks and never a verdict, and no verdict token is
assigned anywhere in `autopilot.py`. The findings paragraph comes from a fixed template — the
objective's value, each check with its found number, the failure that closed an invalid run — and
`crux-close`'s prose is 05.3's. Locking at `running` **after** the worker ran is not laundering:
the pre-registration is the plan, signed once before the run, and the node's checks are copied from
it verbatim.

**The ruling (PI, 2026-09-16).** Inside an approved run the driver performs, per attempt, four acts
that are PI-approved outside a run — `hypothesize`, `approve-null`, `test --to running` and `close` —
and the plan's approval covers all four. `skills/crux/SKILL.md` gains §12's ruling as a new
paragraph at the end of *Three roles — and the leash* naming all four, plus verb-table rows for
`auto approve` (◆, the PI's signature — never run without their yes), `auto run` (◆) and
`auto status` (○), while **the `close` row and the four leash bullets stay byte-unchanged**: outside
an approved autopilot run nothing changes; and `answer`, `approve` on a synthesis, and merging into
`main` stay the PI's inside a run too.

**Rejected: amending the `close` row itself.** One row would carry two regimes, and the assertion
that the leash is unchanged elsewhere stops being a byte comparison.

### E · The state file and the ledger

`auto/<qid>/state.json` is rewritten **whole** after every event, through a temporary file and one
`os.replace`, so it is never half a document. Its keys are a pinned set: run id, plan and its
approved hash, opened and updated times, the driver's pid and host, mode, the effective `c_puct`,
the escalation and steward-requested flags, the base commit, per-island branch, pointer, best and
stall counter, the run's best attempt and score, budget used and total on each axis, the attempts in
flight with their phase, the closed attempts, the consecutive-invalid and stall counters, the
confirmed winner, the stop (null while running), the tasks filed, and the count of ledger events.

`auto/<qid>/ledger.jsonl` is one JSON object per line, appended, never rewritten, and its event
vocabulary is a closed list of seventeen in `engine.py` the driver refuses to write outside:
`run-opened` · `attempt-reserved` · `worker-started` · `worker-done` · `worker-failed` ·
`node-filed` · `scored` · `violation` · `retry` · `closed` · `confirm` · `island-best` · `stall` ·
`escalated` · `abandoned` · `resumed` · `stop`. Both are written only under 05.1's vault lock, in
the same critical section as the write they describe — which is also where `refresh` and the index
files are regenerated, so `META.md` can never be torn by two attempts finishing at once.

**Rejected: deriving the state from the ledger on demand.** §15 needs one small file to read
mid-flight, and a fold over a growing log gets slower the longer the night is.

### F · The phase machine, and what resume does at each phase

An attempt is in exactly one phase, recorded in `state.json` before the work it names, and each
phase leaves durable evidence: `reserved` — an entry in `auto/<qid>/reserved.json`; `drafted` — a
worktree exists for the id; `committed` — `refs/crux/auto/<qid>/<hid>` resolves and the node is in
the vault; `scored` — `results/<hid>/metrics.json` exists; `closed` — the node carries a verdict and
retention has run.

Resume reconciles `state.json` against those five facts rather than trusting it, because the kill
may have landed between the fact and the write: a worktree with a commit and no ref is recorded and
carries on; a ref with no metrics is scored; metrics with no verdict are ticked and closed; a
verdict whose post-close steps did not finish has them finished, never a second close; a reserved
id with no worktree, or a worktree with no commit, is set `abandoned` in `reserved.json` and never
handed out again. A worker still alive from the killed driver is waited for first. **No attempt
whose worker produced a commit is dropped, and no id is closed twice** — that pair is what "nothing
lost, none repeated" means, and both halves are checkable against the five facts and the ledger.
The test-only hook is named here so it is not invented later: `CRUX_AUTO_CRASH_AT=<phase>` makes
the driver kill itself the instant that phase is first recorded — `SIGKILL` where the platform has
it, `SIGTERM` (which is `TerminateProcess`) on Windows — a real kill rather than an exception, so the
test proves recovery from the failure that happens.

**Rejected: a phase counter in one field with no on-disk evidence.** It makes resume trust the
file the crash was most likely to be writing.

### G · The four stops, the island pointer, and what is retried

- **`success`** — an attempt closed `supported`, its objective crossed the bar (inclusive, by the
  plan's direction), and a confirmation passed. The confirmation re-scores **the same commit** at
  `replicates` seeds, `CRUX_SEED=1..N`, none of them the attempt's own `CRUX_SEED=0`, all of which
  must cross the bar; its documents go to `results/<hid>/confirm/<seed>/metrics.json`, so the
  attempt's own `metrics.json` stays the byte-exact object the scorer printed. A seed that misses —
  or whose scorer fails — does **not** touch the verdict: it is a failed `confirm`, and the run
  continues.
- **`budget`** — `budget_attempts` attempts closed, `budget_hours` of the driver's own wall clock
  (summed across resumes, so a night spent dead is not charged), or `budget_model_calls` worker
  invocations; any one ends the run, and the axis is named.
- **`abort`** — `abort_invalid_runs` attempts closing `invalid-run` in a row, or the scorer failing
  on the base commit at run open (checked in a throwaway worktree, before any attempt is reserved).
  Frozen-path and manifest violations close `invalid-run`, so "repeated frozen-path violations" is
  already this counter and needs no second threshold.
- **`stall`** — no improvement of the island's best **score** (any attempt that did not close
  `invalid-run`, starting from the baseline's score) over `stall_attempts` closed attempts on that
  island. It self-escalates **once** per run: Climb raises the effective `c_puct` to the Explore
  value, recorded in `state.json` so selection stays reproducible from the file, and Explore sets
  `steward_requested` for 05.3 to act on. A second stall ends the run.

**The island-best pointer** (§6 step 5, §8). When an attempt closes `supported` and strictly
improves its island's best score by the plan's direction (the baseline's score to begin with), the
driver moves `refs/heads/crux/auto/<qid>/island/<i>` to the attempt's commit with a
compare-and-swap `git update-ref <ref> <new> <old>` and logs `island-best`. These island branches,
plus 05.1's `open_run` branch creation and `promote`, are the **only** writes `autopilot.py` makes
under `refs/heads/`.

**Rejected: a `converged` stop.** §11 rejects it, and the loop is not entitled to the opinion.

**Retries.** `retries` covers the failures that are the machine's: a worker that cannot start, exits
non-zero, produces no commit, or leaves a missing or unparseable proposal or no claim; a claim over
`PROSE_CAP`; and a scorer that exits non-zero, times out or prints no JSON object. Each retry re-runs
the same step in the same worktree, is logged `retry`, and counts a model call when it re-runs the
worker; exhausted, the attempt closes `invalid-run` with a deterministic finding naming the failure.
A scorer whose output parses but whose objective does not resolve is not retried — the document is
written, and the ticks decide.

Three failures are **never** retried, being the worker's act rather than the machine's, which the
same agent would simply repeat at cost: a commit touching a frozen path, a manifest difference
under a shared root outside every attempt workspace of the run, and a proposal carrying a key outside
`{claim, controls}` or a malformed control (not a `{text, fails_if}` object, its own `[kind]` tag,
not a metric comparison, or a repeated failure scenario). Each closes `invalid-run` at once. An
over-cap claim is refused rather than truncated: a truncated claim files a node whose claim is not
what the attempt tested, and the verdict is then recorded against it.

**Rejected: retrying a frozen-path violation.** It pays twice for the same refused act.

### H · Parallelism: one process, polled children

The driver is single-process and threadless. It keeps up to `parallel_total` attempts in flight, at
most `parallel_island` per island, starting them round-robin over the plan's islands, by holding
each worker's `Popen` and polling every 50 ms; scoring, filing and git calls are synchronous. Every
in-flight attempt's parent on an island goes to selection as a virtual visit, which is what 05.0
built the argument for. Vault writes stay serialized behind the lock, so concurrency touches no file
two attempts share. `FANOUT_MAX` is never approached either: a node is filed and moved to `running`
inside one lock hold, so none is left at status `idea` — the only status `unrun_children` counts.

**Rejected: deferring parallelism to 05.3.** The phase machine is per-attempt either way, a
sequential loop would be rewritten into this one, and Explore's default is one attempt per island.

### I · The taskhub: one task per run, filed at the stop

The run gets exactly one task (D15), filed when the run stops, by `cmd_task_add` with
`hypothesis_refs` naming the run's best closed attempt and its derived verdict, then
`cmd_task_done` with that node as the output. `experiment` is a **computed** category — a task is
one when it says what it concluded about a hypothesis — so a task filed at run open could only be
an ordinary chore, and a chore is not PI-gated, which is exactly the signature §14 asks for. Filed
at the stop it lands in `crux task review`, where accepting it pairs with the merge decision the PI
makes in the morning. A run that closed no attempt files an ordinary, done task instead. The
exception earns its own task: an `abort` stop, and any attempt that exhausts its retries, files one
open ordinary task, putting it in the frontier. Every task the driver files carries the category
`autopilot`, which the driver declares the existing way (`cmd_task_categories(add=…)`) when the
vault does not list it.

**Rejected: filing the run's task at run open.** It cannot carry a conclusion yet, and no verb
adds one afterwards.

## Scope — what this does not do

- **No agents.** `crux-auto-worker`, `crux-auto-steward`, the agent template's failover walk, §11's
  rate-limit failover and `crux-close` wired in are all 05.3; here the `agent:` command is run as a
  subprocess exactly as written, once per try, and a stub script stands in for it.
- **No steward, and no new islands.** `steward: true` is refused, and islands are the plan's
  declared islands, because opening one is a judgment (D14) whose judge arrives in 05.3.
- **No cockpit** (05.4) and **no setup skill** (05.5): this slice fixes the state file the cockpit
  will read, not how it is drawn. **No prose checks** until 05.3 wires `crux-close`. **No new
  verdict path** — `derive_verdict_15` and `cmd_close` are untouched and the driver supplies ticks.
- **No commits (PI, 2026-09-16).** Vault writes stay **uncommitted** in the checkout that holds the
  vault. The loop commits nothing on any branch, and the run branch receives no commits in 05.2:
  spec §8's "every write the loop makes lands under the run branch" is deferred. **`main` is never
  written**, checked out or merged; the island branches move only as G says.
- **No report link.** The driver writes `results/<hid>/metrics.json` but links no report under
  `## Artifacts`, so `validate`'s existing "files but no report" problem fires on attempt nodes, as
  it already does on the 05.0/05.1 fixtures; `crux-close` writes the report in 05.3.
- **`auto check` is unchanged** in output: approval state is read by `auto run` and `auto status`.

## Acceptance criteria

- [x] A worker command exiting non-zero, and a scorer crashing on an attempt, are each retried
      `retries` times and then close the attempt `invalid-run`, never `refuted`.
- [x] An attempt with no metrics file closes `invalid-run` because every check ticks `[-]` — and
      the verdict equals `derive_verdict_15` over that vector, computed independently in the test.
- [x] A worker commit touching a frozen path, and a worker writing under a declared shared root
      outside its own workspace, each close `invalid-run` with **no** retry, and the ledger carries
      one `violation` event naming the path or the file.
- [x] A check reading `obj.score >= -0.5` ticks `[x]` at 0.0 and `[ ]` at -9.0, each ticked line
      carrying a `(found: …)` note, and neither tick nor note raises `lock_drift`.
- [x] A plan carrying a check with no leading metric comparison is refused under `check-grammar`,
      and `≤ ≥ ≠` parse as `<= >= !=`.
- [x] A static scan finds no verdict token assigned anywhere in `autopilot.py`, and every closed
      attempt's verdict matches `derive_verdict_15` recomputed from its own node.
- [x] A proposal whose claim would put the node over `PROSE_CAP` is refused and retried, closes
      `invalid-run` after `retries`, and files no node with a truncated claim.
- [x] A proposal carrying a key outside `{claim, controls}`, or a `controls` entry with its own
      `[kind]` tag, closes `invalid-run` unretried; a good one is filed `[outcome-neutral]`.
- [x] Resume records an attempt with a commit and no ref, scores one with a ref and no metrics,
      closes one with metrics and no verdict, and marks a bare reserved id `abandoned` without

- [x] A run killed via `CRUX_AUTO_CRASH_AT` at each of the five phases resumes to the same

- [x] The stall fixture escalates exactly once — one `escalated` event, `c_puct` raised to the
      Explore value in `state.json` — and a second stall stops the run `stall`.
- [x] Across a full tier-0 run no question holds an unrun hypothesis, so `fanout_pressure` never
      fires and `validate` reports no fan-out problem.
- [x] `skills/crux/SKILL.md` carries the §12 ruling naming the four acts (`hypothesize`,
      `approve-null`, `test --to running`, `close`), and the `close` row and the four leash bullets
      are byte-identical to their pinned text.
- [x] A hypothesis closed by hand outside `auto/` at the same tick vector yields the same verdict
      and the same node bytes as before this slice, and writes no state or ledger file.
- [x] After a full tier-0 search `git rev-parse main`, `git symbolic-ref HEAD` and
      `git rev-parse HEAD` are unchanged, and `git status --porcelain` is empty outside the vault
      directory and the plan's writable roots.
- [x] `auto run` refuses, before any reservation, a plan with `steward: true`, a plan whose
      `replicates:` holds no integer, and a plan `auto check` reports a problem on.
- [x] `auto run`, `auto status` and `auto approve` emit parseable JSON under `--json`; `auto status`

- [x] A static scan finds `engine.py` starting no process and naming no git command, and

- [x] A vault with no `auto/` directory loads, validates and renders unchanged under this engine,

- [x] `auto approve` stamps `approved` and `approved_hash` once and is idempotent; guidance
      appended with `auto guide` keeps the approval, and any other edit to the plan clears it.
- [x] `auto run` refuses, before any reservation, a plan that is not approved and a plan edited
      after its approval, each with its pinned message naming `crux auto approve`.
- [x] The island branch moves by compare-and-swap to an attempt's commit only when it closes

- [x] An Explore attempt whose parent sits under another question is filed under its island with

- [x] Each attempt is filed at its reserved id through `hypothesize`, `approve-null`,

## Backward-compat / migration

**No vault format change, so `ENGINE_VERSION` does not bump, and there is no migration.** Every
node the driver files is an ordinary idea node with the `builds_on:` field 05.0 already added;
`state.json` and `ledger.jsonl` are not nodes, enter no roll-up and are read by no view; and the
comparison is text inside an existing check line, so `_verifiables()`, `count_verifiables_by_kind`,
`lock_material` and `derive_verdict_15` are byte-unchanged. What closes an attempt is `cmd_close`,
unchanged, reached by a new caller.

This **supersedes 05.1's forecast** that the bump would come here. That line predates the close
path's design; the gate's rule is format or verdict/roll-up/view logic, this slice changes none of
the three, and a bump would move a version boundary load-bearing elsewhere for no rule binding to
it.

Additions that tighten what a plan may say, none touching a vault: `auto check` gains
`check-grammar` and a `replicates` integer check, both refusing before any attempt is reserved, and
a plan is not a node; `approved:`/`approved_hash:` are optional plan fields that no check reads.
Additions to existing functions, each optional and each leaving every current caller unchanged:
`cmd_hypothesize` gains `nid=` (file at the id 05.1 reserved rather than allocating a second) and
